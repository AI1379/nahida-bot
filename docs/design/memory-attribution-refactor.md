# 记忆归属与统一读写入口重构

> 日期：2026-10-30
> 状态：代码重构已实现并通过回归验证；生产部署和历史数据修复尚未执行。
> 关联：[记忆去冗余提案](memory-simplification-proposal.md)、
> [记忆软 scope](memory-soft-scope-and-authz.md)、[身份系统](person-identity-system.md)。

## 1. 问题定义

当前数据流不能持续回答三个问题：这件事说的是谁、证据来自哪里、在当前对话中应如何解释。
原始发言有身份，dream 输入丢弃身份；检索结果有 scope，提示词渲染又丢弃来源。
共享 Markdown 则直接绕过检索入口。各模块分别完成自己的操作，但组合之后不保持记忆归属。

生产核查确认：

- 共享工作区 `MEMORY.md` 的前 6000 字中，34 个结构化记忆 ID 属于同一游戏群。
  2026-10-29 至 10-30 采样的 656 次上下文构建、120 个独立 trace 均加载共享 Markdown。
- 北京时间 10-23 起新增的 775 条后台群记忆中，629 条包含含糊的“用户”；
  这些后台群记忆均无结构化人物主体字段。含“用户”不等于已证实内容错误。
- 199 次 dream 中有 22 次失败后仍推进处理水位；从原始发言重建后，至少 50 批输入
  在压缩空白后仍超过 2000 字符。失败和截断计数存在重叠。

7 月去冗余提案已经提出共享 workspace 与 scope 映射问题，但当前实现仍把某一 scope
的结果写入共享文件。只过滤 sensitivity 无法保证人物归属、上下文适用性或 portable 约束。

## 2. 需要调整的职责

| 当前实现 | 缺口 | 重构后的责任 |
|---|---|---|
| `MemoryService.search_items_cascade` 与 `MemoryStoreRetrievalAdapter._cascade` | 各自实现范围级联；工具读主要走 FTS，自动召回可走 hybrid | 一个记忆读取用例统一策略；检索适配器负责检索算法 |
| `MemoryService.store_item` 与 `MemoryConsolidator.consolidate_turn` | 各自决定写入范围、打标并落库 | 同一个写入策略和应用变更入口；不同来源保留显式差异 |
| `SchedulerService._dream_session` | 拼提示文本、选择消息、调用整理、推进水位 | scheduler 只负责触发；记忆子包拥有批次处理及成功语义 |
| `ContextBuilder`、`memory_read`、Markdown 投影 | 共享文件成为额外读取路径 | 所有模型可见的动态记忆通过统一读取用例 |
| `SessionRunner`、`MemoryTools.format_refs`、`MemoryRef` 转换 | 多次裁剪字段，主体和证据无法贯穿 | 一个模型可见记忆视图和格式化实现 |
| `scope`、任意 `metadata` / `evidence` 字典 | 作用域同时被当作人物、来源和适用范围 | 明确主体、来源、归属范围、敏感度和可迁移性 |

保留 `agent/memory/` 现有包位置，并使 `MemoryService` 成为实际统一入口。
SQLite store/repository 继续负责存储；检索基础设施继续共享给 KB。
操作员管理接口保留显式的管理视图，与面向对话的读取用例分开，复用数据模型和变更校验。
记忆策略继续与工具动作授权解耦。

## 3. 首先明确的数据契约

### 3.1 主体与证据

在模型层增加有类型、有校验的主体和证据对象，并通过统一的序列化边界兼容现有 JSON 列。
普通调用方不再直接拼接随意的 metadata 键。

- `MemorySubject`：事实讨论的 person/account，或明确的群体/项目/未知主体。
  确定的跨账号身份只使用现有 identity 解析结果。
- `EvidenceRef`：原始 turn ID、消息 ID、来源 chat、发言者账号、时间和角色；保留引用关系。
  来源字段从实际消息读取，模型不能自行编造来源 ID。
- `scope`：记忆的主要归属范围；不能单独证明事实的主体，也不代替来源 chat。
- `sensitivity`：内容是否受限；`portable`：内容能否离开原上下文成立。
  两者独立于“这是谁的事情”。

例：甲说“乙喜欢咖啡”，发言者是甲，事实主体是乙，证据是甲的陈述。
不能因为本轮 sender 是甲，就把这条写成甲的个人偏好。群内昵称也不能自动建立 Person 关联。
转发、引用、助手推断和当事人自述需要保留区别。

旧条目缺失主体时显式标为未知，不能根据当前读者或最后一名发言者补齐。
未知主体的个人经历不自动当成当前用户的事实；可作为待核对线索返回，并保留来源和不确定性。
跨群回忆仍然可用，既有受限内容规则继续生效。

### 3.2 变更与成功状态

整理器返回明确的 `ConsolidationOutcome`，区分成功无变化、成功有变化、失败。
候选里引用的证据必须来自本批次，归档/替换的对象必须在允许修改的范围内。
模型返回的置信度只是一项信息，不能代替这些校验。

写入工具与后台整理都生成候选变更，进入同一校验和应用路径。
显式打标与自动推断的优先级仍然保留；来源的差异通过类型和参数表达。

## 4. 读取流程

```text
当前对话身份 + 查询 + 读取意图
  → MemoryService：解析适用范围、筛选候选
  → 检索适配器：FTS / 向量 / hybrid / 字面检索
  → 保留主体与证据的记忆视图
  → 统一格式化
  → 自动注入或 memory_read 工具结果
```

自动召回、显式查询和跨群探索可以有不同预算、排序或范围扩张规则，差异必须是显式选项。
相同选项应执行相同的边界规则；不能由调用入口偶然决定是否保留来源。
每条输出至少说明主体、来源群/私聊、时间、事实及证据引用。
裁剪预算时优先减少条目或正文，不能留下脱离主体和来源的半条记忆。

`ContextBuilder` 只组装已准备好的消息，不自行发现和加载动态记忆文件。
`memory_read` 不再把共享 Markdown 追加到结构化结果之后。
原提案需要保留的“按原话或子串查找”能力由同一读取入口提供，排序未命中时仍可查找。
Markdown 保留为显式导出/诊断形式，标明导出范围和时间，不成为自动或工具回退的第二来源。
旧文件的手写内容须单独审核并迁移；常驻人物设定也必须明确其受众与加载规则。

## 5. 整理流程

```text
scheduler 触发
  → 读取已处理水位之后的原始消息
  → 按完整消息构造带身份的批次
  → LLM 提出候选变更
  → 校验证据、主体和修改范围
  → 原子应用变更与推进水位
  → 异步刷新派生索引
```

- 不再只取“最新 40 条”后跳过中间积压；按水位升序读取，预算不足的部分留给下一批。
- 不截断拼接文本的前 2000 字符；按完整消息预算分批。单条超限须显式处理并记录，
  不能无声推进。前序上下文可作为只读参考，须与本批次新增证据区分。
- LLM 调用在数据库事务外。成功后在短事务内应用记忆变更并推进水位；
  提交时检查起始水位，防止同一批次重复提交。进程失败不能留下“记忆写入了但水位没写”的半次应用。
- provider 失败、解析失败或校验未通过不当作成功空结果。为持续无法处理的批次提供重试状态和
  明确的隔离处理，不能无限忙重试，也不能悄悄越过。
- embedding 更新失败独立记录和补偿，不让已提交记忆再次被生成。
- 旧记忆、检索片段和助手复述只作为参考，不能循环充当新事实的独立证据。

## 6. 分阶段交付与验收

1. **切断共享文件路径，统一记忆展示。** 同时覆盖自动注入和 `memory_read`，保留带边界的
   字面查询。两群共用工作区时，B 的投影不得覆盖 A 的模型上下文；可跨群内容必须显示来源。
2. **收拢读写用例，补齐主体与证据契约。** 自动召回、工具、后台整理使用共同入口。
   验证同群多人物、第三人陈述、引用/转发、别名和跨账号身份，避免默认绑定当前 sender。
3. **迁出 scheduler 的整理业务，修复批次提交。** 覆盖失败、截断、积压、重试和提交中断。
   一条位于长对话末尾的纠正不能被标记为已处理却未送入整理。
4. **历史修复预演。** 对数据库一致性副本分类处理；有可靠原文的补回来源和主体，
   主体不明的个人条目隔离/归档，保留可恢复记录。先输出差异清单，再实施生产清理。

测试以可观察行为为准：使用两名发言者、两个群、一个共享 workspace，跑过完整的整理→存储→
工具读取/自动提示链路。现有只验证“投影不含 private/secret_like”的测试不足以覆盖归属问题。
另验证相同读取选项的工具与自动入口一致，公开且允许迁移的正确记忆仍可跨群回忆。

记录批次 ID/水位、证据 ID、候选接纳/拒绝原因、召回来源和裁剪原因，便于排查具体错答。
普通日志不必重复输出完整私人原话。

此次范围保持在现有记忆链路及其调用方；原始发言与提炼记忆继续分层，KB 生命周期保持独立。
生产数据清理在新入口验证后单独执行，不混在代码部署中。

## 7. 实现落点与上线准备（2026-10-30）

- `agent/memory/attribution.py`：有类型的主体和原始证据；账号、原群、消息 ID、时间、角色及触发来源随记忆保存。
- `write_policy.py`：工具、整理器及更新操作共享写入策略；未知主体不继承当前说话者，更新保留原主体。
  有证据的群聊记忆仍归属原群，人物主体单独保存，因此关闭 soft-scope 后仍可在原群召回。
- `service.py` / `retrieval/adapters.py`：共用一个范围级联实现；自动跨群候选在 SQL LIMIT 前筛选明确主体，
  旧记录仍可显式查询并显示未知归属。FTS 无命中时使用同边界的字面子串查询。
- `rendering.py`：工具与自动提示统一显示主体、来源、时间和证据 ID。共享 Markdown 不再自动注入或作为工具回退。
- `dreaming.py`：按水位读取最早的完整待处理消息；成功变更与水位一起提交，失败保留水位，重试提交检查原水位。
  单条超过预算会记录需要审阅的错误，不截断后悄悄跳过。
- `memory_candidates` 继续承担审计：证据缺失、主体未知或未经验证的候选保持 pending，并记录拒绝原因及原批次 turn ID。
  已安全隔离的候选允许批次推进；模型调用/解析失败则不推进。没有新增数据库表或迁移历史条目。

只读预演命令（对归档的一致性副本运行）：

```powershell
uv run python scripts/audit_memory_attribution.py --database <snapshot.db> --output <attribution-audit.json>
```

报告逐条列出归属或证据缺失，不代表这些内容全部错误；脚本不推断人物、不调用模型、不修改数据库。
上线前保留数据库一致性备份及旧 `MEMORY.md` / `memory_summary.md`，核对手写常驻内容的迁移需要。
上线后验证共享文件不再进入模型上下文、失败批次保留水位、普通群记忆仍能召回，再单独审阅历史修复清单。
跨账号 Person 合并仍只由现有身份系统决定；后台提取使用已观测账号，不从姓名或昵称推断同一人。

验证记录：独立工作树全量非联网测试 3000 passed、2 skipped（Windows）、15 deselected；
最后补充的显式跨群回忆/归属校验通过 139 项定向测试，导出视图通过 161 项定向测试。
Ruff、全仓格式检查及 Pyright 在隔离基线上执行；生产服务和记忆库未修改。
显式跨群回忆保留原始发言者及长期记忆主体，转述结果明确显示证据作者。
